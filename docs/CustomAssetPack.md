# `CustomAssetPack` — the tiny-pack-stub pattern

This document describes the pack-entry IMod
[`CustomAssets.CustomAssetPack`](../src/CustomAssetPack.Lib/CustomAssetPack.cs) and
its abstract implementation
[`CustomAssets.CustomAssetPackBase`](../src/CustomRecipes/CustomAssetPackBase.cs),
and how to use them to ship a sub-mod ("pack") with a ~5 KB stub DLL instead
of a full-size per-pack assembly.

It complements [MODDING.md](MODDING.md), which covers Python-side authoring of
recipes and prototypes. This document is about the **C# integration surface** a
pack uses to plug into Captain of Industry.

## Where the C# lives

The C# is split across two assemblies so a pack folder only ships the small
piece that needs per-pack identity:

| Assembly | Built from | Contains | Shipped where |
| --- | --- | --- | --- |
| `CustomAssets.dll` (~217 KB) | [`src/CustomRecipes/`](../src/CustomRecipes/) | `CustomAssetsMod` (base mod IMod), `CustomAssetPackBase` (abstract pack-entry implementation), `EmittedPackMod` (abstract emit marker), `CustomAssetRegistrator`, `CustomAssetManager`, PythonAPI, all runtime helpers | Base CustomAssets mod folder only — loaded once, shared by all packs |
| `CustomAssetPack.dll` (~5 KB) | [`src/CustomAssetPack.Lib/`](../src/CustomAssetPack.Lib/) | Sealed concrete `CustomAssetPack : CustomAssetPackBase` — single ctor, no logic | Every pack folder. Also **staged** inside the base CustomAssets folder (not loaded) for the pack generator to scaffold new packs from |

At runtime each pack's `CustomAssetPack.dll` is loaded under
`non_locking_dll_load` and gets its own CLR Assembly instance. References from
`CustomAssetPack.dll` into `CustomAssetPackBase`, `CustomAssetRegistrator`,
etc. all resolve to the **single** base-mod `CustomAssets.dll` that the pack's
`mod_dependencies` forced to load first. Each pack still has a distinct CLR
`CustomAssetPack` Type (per-pack assembly load) — that's the property that
satisfies Mafi's `HashSet<Type>` dedup inside `ProtoRegistrator`.

## Why this exists

The original sub-mod pattern (still supported, see
[`src/CustomAssetPack/Generated/CustomAssets_IronPlateRecyclation/`](../src/CustomAssetPack/Generated/CustomAssets_IronPlateRecyclation/)
for a live example) generates **one DLL per pack** at build time, each
containing a uniquely-named `DataOnlyMod` subclass like
`class CustomAssets_IronPlateRecyclation : DataOnlyMod { ... }`. Pack identity
is the CLR class name; uniqueness is satisfied at compile time.

That works, but ModBuilder has to scaffold a `<PackId>.csproj` per pack and
every pack rebuild goes through `csc`.

The `CustomAssetPack` pattern replaces that with two pieces:

- A **shared abstract implementation** `CustomAssetPackBase` lives once in the
  base mod's `CustomAssets.dll`. All the pack-entry logic
  (`RegisterPrototypes`, the `RegisterDependencies` emit step, the IMod
  property surface) is here. Updating pack behavior means rebuilding only the
  base mod.
- A **tiny sealed concrete stub** `CustomAssetPack : CustomAssetPackBase`
  lives in `CustomAssetPack.dll` (~5 KB). The stub adds zero logic — it just
  exists so Mafi can find a class named `CustomAssetPack` via
  `primary_mod_class_name` and instantiate it.

The pack's manifest sets `non_locking_dll_load: true`, which makes Mafi call
`Assembly.Load(File.ReadAllBytes(dll))`. Each call returns a **fresh** CLR
`Assembly` instance — even when the bytes are identical across packs. So each
pack's `CustomAssetPack` is a **different `System.Type` instance** at the CLR
level. Mafi's `HashSet<Type>` dedup treats them as distinct, and
`CustomAssetRegistrator` (resolved from the single base-mod assembly) runs
cleanly per pack.

Net effect: zero per-pack code generation, ~5 KB per-pack binary, and a single
shared abstract implementation that owns all the pack-entry logic.

## Two patterns side by side

| | **Legacy: per-pack DLL** | **New: `CustomAssetPack`** |
| --- | --- | --- |
| Per-pack files generated by ModBuilder | `Generated/<PackId>/<PackId>.cs` + `.csproj` + `bin/...` | none |
| Per-pack DLL shipped | `<PackId>.dll` (~few KB) | `CustomAssetPack.dll` stub (~5 KB) |
| Pack manifest `primary_dlls` | `["<PackId>.dll"]` | `["CustomAssetPack.dll"]` |
| Pack manifest `primary_mod_class_name` | not required (single IMod per pack DLL) | **required**: `"CustomAssetPack"` |
| IMod CLR Type seen by Mafi | `<PackId> : DataOnlyMod` — unique by definition | `CustomAssets.CustomAssetPack` — unique per-pack via assembly-load isolation |
| Build step | `csc` per pack | `csc` once for `src/CustomAssetPack.Lib/`; same stub DLL is shipped to every pack folder |
| Both patterns can coexist | yes — currently five packs on the legacy pattern, two on the new |

You can migrate packs one at a time. Packs already on the new pattern at the
time of writing: **Batteries**, **AirFiltering**.

## Pack folder layout

A pack is a folder under `src/CustomAssetPack/Packs/<PackName>/` containing:

```
Packs/MyPack/
  manifest.json         ← required, fields shown below
  thumbnail.png         ← optional, shown in the in-game mod browser
  thumbnail.svg         ← optional, rasterized to thumbnail.png at build time
  config.json           ← optional, JSON-based mod settings
  Assets/               ← optional, icons + asset bundles
    Icons/MyIcon.svg    ← .svg sources are rasterized to .png by ModBuilder
    Icons/MyIcon.png    ← .png artifacts are deployed (the .svg is excluded)
  Definitions/          ← Python recipe/prototype definitions
    __init__.py         ← preferred entry point (loaded first)
    my_recipe.py
    my_product.py
```

Pack authors write **zero C#**. All content is in `Definitions/*.py`. See
[MODDING.md](MODDING.md) for the Python authoring side.

## `manifest.json` — the three load-bearing fields

```json
{
  "id": "CustomAssets_MyPack",
  "display_name": "My Pack [CAL]",
  "version": "0.0.1",
  "description_short": "Short description shown in mod list.",
  "description_long": "Longer description shown in the mod browser. Multi-line via \\n.",
  "authors": [ "YourName" ],
  "mod_dependencies": [
    "CustomAssets>=0.1.9"
  ],
  "min_game_version": "0.8.4",
  "non_locking_dll_load": true,
  "primary_dlls":            [ "CustomAssets.dll" ],
  "primary_mod_class_name":  "CustomAssetPack",
  "can_add_to_saved_game":    true,
  "can_remove_from_saved_game": true
}
```

Three fields are what make the pattern work:

| Field | Required value | Why |
| --- | --- | --- |
| `non_locking_dll_load` | `true` | Mafi calls `Assembly.Load(File.ReadAllBytes(dll))` instead of `Assembly.LoadFrom`. `Load(bytes)` always creates a fresh CLR Assembly instance, which is what gives each pack its own distinct `CustomAssetPack` Type. With `LoadFrom`, Mafi could return a cached Assembly and break the per-pack Type identity. |
| `primary_dlls` | `["CustomAssetPack.dll"]` | The pack ships only the ~5 KB stub DLL. Type references inside the stub (`CustomAssetPackBase`, `CustomAssetRegistrator`, etc.) resolve at runtime to the base mod's already-loaded `CustomAssets.dll`. |
| `primary_mod_class_name` | `"CustomAssetPack"` | The stub DLL contains exactly one IMod-derived class — `CustomAssetPack` — so this field is technically redundant for the stub-only case, but **must still be set** because Mafi requires it when the assembly was compiled against a base assembly that has other IMod types visible. Set it explicitly to be safe. |

The other fields are standard — `id` must match the deployed folder name under
the COI Mods directory, and `mod_dependencies` **must** include CustomAssets so
COI loads the base mod before any pack. Without that load order, the pack
stub's runtime references to `CustomAssetPackBase` and the registrar would
fail to resolve when the pack's CLR JIT touches them.

## Wiring the pack into the build

In [`src/CustomAssetPack/CustomAssetPack.csproj`](../src/CustomAssetPack/CustomAssetPack.csproj):

**(1)** Exclude the pack from the legacy per-pack-DLL pipeline by adding to
the existing `<ItemGroup>` of `Remove` directives:

```xml
<Compile          Remove="Packs\MyPack\**" />
<EmbeddedResource Remove="Packs\MyPack\**" />
<ModFolders       Remove="Packs\MyPack\**" />
<None             Remove="Packs\MyPack\**" />
```

This stops ModBuilder from scaffolding a `Generated/<PackId>/` csproj for it.

**(2)** Register the pack with the new-pattern deploy target by adding to the
`<NewPatternPack>` `<ItemGroup>`:

```xml
<NewPatternPack Include="MyPack">
  <ModId>CustomAssets_MyPack</ModId>
</NewPatternPack>
```

The `Include` value is the **folder name** under `Packs/`. The `<ModId>` is the
`id` from your manifest — used as the destination folder name in the COI Mods
directory. They differ only because the folder convention is shorter than the
full mod id.

## Build + deploy

```bash
# Build the stub DLL (transitively builds CustomAssets.dll too via ProjectReference):
dotnet build src/CustomAssetPack.Lib/CustomAssetPack.Lib.csproj -c Debug

# Deploy all packs registered as NewPatternPack:
dotnet msbuild src/CustomAssetPack/CustomAssetPack.csproj \
    -t:DeployNewPatternPacks -p:Configuration=Debug
```

Building `CustomAssetPack.Lib.csproj` does three things:

1. Builds `src/CustomRecipes/CustomAssets.csproj` (via ProjectReference). Its
   PostBuild deploys the base mod into
   `%APPDATA%/Captain of Industry/Mods/CustomAssets/` (manifest, AssetBundles,
   API/, recipes, `CustomAssets.dll`, `CustomAssets.pdb`).
2. Builds `CustomAssetPack.dll` into `src/CustomAssetPack.Lib/bin/.../`.
3. Runs `StagePackStubInBaseMod` — copies `CustomAssetPack.dll` into the base
   CustomAssets mod folder as a **staged artifact** for the in-progress pack
   generator. The base mod's manifest's `primary_dlls` stays
   `["CustomAssets.dll"]`, so Mafi never tries to load this staged copy as
   part of the base mod. It just sits there.

For each `<NewPatternPack>` entry, `DeployNewPatternPacks` does:

1. Rasterizes any `Assets/**/*.svg` and pack-root `thumbnail.svg` to PNG.
2. Deletes stale artifacts from prior pattern variants in the deploy folder:
   the legacy per-pack `<ModId>.dll`/`.pdb`, and any old full-size
   `CustomAssets.dll`/`.pdb` from the intermediate pattern that shipped the
   full base mod in each pack folder.
3. Copies `manifest.json` + optional `config.json` + `thumbnail.png` +
   `Assets/**/*` (excluding `.svg`) + `Definitions/**/*` into
   `%APPDATA%/Captain of Industry/Mods/<ModId>/`.
4. Copies the freshly-built `CustomAssetPack.dll` (and `.pdb` for Debug
   configuration) into the same folder. **No `CustomAssets.dll`** is copied —
   the pack relies on the base mod's loaded copy via runtime assembly
   resolution.

All steps are idempotent — re-running them just refreshes the deploy.

### Fast core-iteration loop: `Core_Only`

When you're iterating on the core mod's C# (PythonAPI, asset loading,
registrar internals) and don't want to wait for the 5 legacy packs to be
regenerated or the 2 new-pattern packs to be redeployed, build the orchestrator
with the `Core_Only` Configuration:

```bash
dotnet build src/CustomAssetPack/CustomAssetPack.csproj -c Core_Only
```

This skips:

- The `BuildAll` target (generates + builds the 5 legacy packs).
- The `DeployNewPatternPacks` target (deploys Batteries + AirFiltering with
  the stub).

And still does:

- Build `CustomAssets.dll` via the `ProjectReference`.
- Run its PostBuild → deploy the base mod to `%APPDATA%/.../CustomAssets/`.

The previously-staged `CustomAssetPack.dll` in the base mod folder is left
untouched (it's only restaged when you rebuild the Lib project itself), and
already-deployed pack folders are left alone too. So COI sees fresh core code
on next launch with no pack-side churn.

## Lifecycle in COI's load sequence

Mafi calls these methods on `CustomAssetPack` (which inherits them all from
`CustomAssetPackBase` in the base mod's `CustomAssets.dll`) in this order, per
pack:

| Phase | Method | What happens |
| --- | --- | --- |
| 1. Construct | `CustomAssetPack(ModManifest)` (delegates to `CustomAssetPackBase`'s protected ctor) | Stores `Manifest`, builds `JsonConfig`. Logs `"<ModId>: pack constructed (CustomAssetPack entry)"`. |
| 2. Register prototypes | `RegisterPrototypes(ProtoRegistrator)` | Calls `new CustomAssetRegistrator().RegisterData(registrator)`. The registrator reads `Manifest.RootDirectoryPath/Definitions/*.py` and translates them into Mafi prototypes. Asset paths in the Python files are resolved relative to the manifest folder. Logs `"<ModId>: pack registering prototypes"`. |
| 3. Register dependencies | `RegisterDependencies(DependencyResolverBuilder, ProtosDb, bool)` | Emits a dynamic CLR Type named exactly `Manifest.Id`, inheriting [`EmittedPackMod`](../src/CustomRecipes/EmittedPackMod.cs). Pre-constructs an instance with `(Manifest, JsonConfig)` and registers it via `RegisterInstance(instance).AsSelf().As<IMod>()`. Logs `"<ModId>: emitted+registered marker type <ModId>"`. |
| 4. Early init | `EarlyInit(DependencyResolver)` | No-op. |
| 5. Initialize | `Initialize(DependencyResolver, bool)` | No-op. |

A typical log excerpt for two packs loading side by side:

```
~Mai: CustomAssets:               constructed
~Mai: CustomAssets_AirFiltering:  pack constructed (CustomAssetPack entry)
~Mai: CustomAssets_Batteries:     pack constructed (CustomAssetPack entry)
~Mai: CustomAssets:               registering prototypes
~Mai: CustomAssets_AirFiltering:  pack registering prototypes
~Mai: CustomAssets_Batteries:     pack registering prototypes
~Mai: CustomAssets_AirFiltering:  emitted+registered marker type CustomAssets_AirFiltering
~Mai: CustomAssets_Batteries:     emitted+registered marker type CustomAssets_Batteries
```

## How the dynamic Type emission works

`CustomAssetPackBase.RegisterDependencies`
([src/CustomRecipes/CustomAssetPackBase.cs](../src/CustomRecipes/CustomAssetPackBase.cs))
uses `System.Reflection.Emit` to build a per-pack dynamic assembly:

```csharp
var asmName    = new AssemblyName("CustomAssetPack.Emitted." + manifest.Id);
var asm        = AssemblyBuilder.DefineDynamicAssembly(asmName, AssemblyBuilderAccess.Run);
var module     = asm.DefineDynamicModule(asmName.Name);
var typeBldr   = module.DefineType(
    manifest.Id,                                                  // Type.Name = ModId
    TypeAttributes.Public | TypeAttributes.Class | TypeAttributes.Sealed,
    typeof(EmittedPackMod));                                      // base class
// ... emit ctor IL that forwards (ModManifest, ModJsonConfig) to base ...
var emittedType = typeBldr.CreateType();
var instance    = (IMod)Activator.CreateInstance(emittedType, manifest, jsonConfig);
depBuilder.RegisterInstance(instance).AsSelf().As<IMod>();
```

A few non-obvious choices:

- **`AsSelf()` keys on `instance.GetType()`**, not `typeof(T)` — verified in
  [Mafi/DependencyResolverBuilder.cs:96-100](https://github.com — see decompile).
  So the DI registration key is the *emitted* Type whose name equals the
  manifest id, not the generic `EmittedPackMod` base.
- **The instance is pre-built** instead of using `RegisterDependency(type)`.
  Mafi's resolver tries to auto-construct registered IMod implementations
  during `AllImplementationsOf<IMod>` resolution (called from
  `TerrainManager.initAfterLoad` during save load). Auto-construction would
  fail because `ModManifest` is not a registered DI service. Pre-building the
  instance and using `RegisterInstance` makes DI return the existing instance
  without ever invoking the constructor.
- **`AssemblyBuilderAccess.Run`** (not `RunAndCollect`) keeps the dynamic
  assembly alive for the process lifetime. The emitted Type is held by the DI
  container, so it would not be GC'd anyway, but `Run` matches the lifetime
  semantics of the pack itself.

This whole mechanism is **preparatory infrastructure**. Today nothing reads
back the emitted marker — but it makes the pack identity introspectable as
a CLR Type via `AppDomain.GetAssemblies()` or DI queries, which downstream
features (a pack-enumeration UI, cross-pack registration handlers, etc.) can
build on without changing the per-pack contract.

## Verifying in-game

After deploying and launching COI, check the log at
`%APPDATA%/Captain of Industry/Logs/<latest>.log` for these markers per pack:

| Log line | Meaning |
| --- | --- |
| `Mod '<ModId>' loaded, found IMod types: CustomAssetPack, CustomAssetsMod, EmittedPackMod` | Mafi enumerated the three IMod types in the per-pack `CustomAssets.dll` load. PrimaryModClassName selects `CustomAssetPack`. |
| `<ModId>: pack constructed (CustomAssetPack entry)` | Constructor ran with the pack's manifest. |
| `<ModId>: pack registering prototypes` | `RegisterPrototypes` ran. CustomAssetRegistrator is reading the pack's `Definitions/*.py`. |
| `<ModId>: emitted+registered marker type <ModId>` | Reflection.Emit succeeded; the marker instance is in DI. |

If `RegisterPrototypes` runs without any `Data class 'CustomAssetRegistrator'
was already registered, skipping` error, assembly-load isolation is doing its
job — each pack's `CustomAssetRegistrator` is a distinct CLR Type from the
others' and from the base mod's.

## Known quirks and warnings to ignore

When two or more packs use the new pattern, the log shows three warnings
during `RegisterDependencies`:

```
W ~Mai: Dependency implementation 'CustomAssets.CustomAssetPack' is already registered for type 'CustomAssets.CustomAssetPack'.
W ~Mai: Dependency implementation 'CustomAssets.CustomAssetPack' is already registered for type 'Mafi.Core.Mods.IMod'.
W ~Mai: Dependency implementation 'CustomAssets.CustomAssetPack' is already registered for type 'System.IDisposable'.
```

These come from Mafi's `GameBuilder.registerDependenciesOrThrow` calling
`RegisterInstance(mod).AsSelf().AsAllInterfaces()` for every IMod. Mafi's
internal `Lyst<Type>` dedup compares Types by full name string, so the
second-and-later packs' `CustomAssetPack` registrations are flagged as
duplicates even though they're distinct CLR Types from different Assembly
instances. The warnings are harmless:

- The emitted marker Types have unique names (`Manifest.Id`) so **those** do
  not collide.
- Mafi's mod lifecycle iterates its own mod list, not DI resolutions, so all
  packs still get constructed, get `RegisterPrototypes` called, and so on.
- The DI inconsistency only affects code that does
  `resolver.Resolve<CustomAssetPack>()` — which nothing currently does.

If you ever need a DI handle to a specific pack's instance, look it up by the
emitted Type (name = manifest id), not by `CustomAssetPack`.

## Troubleshooting

**Mafi error: `Mod 'X' has multiple IMod implementations (CustomAssetPack,
CustomAssetsMod, EmittedPackMod). Exactly one is required.`**
→ You forgot `"primary_mod_class_name": "CustomAssetPack"` in `manifest.json`.

**Mafi error: `primary_mod_class_name 'X' but no IMod implementation with
that class name was found.`**
→ Your `primary_mod_class_name` doesn't match a class in `CustomAssets.dll`.
The valid values are `"CustomAssetsMod"` (for the base mod itself) and
`"CustomAssetPack"` (for any pack).

**Log says `emit+register pack marker failed: ArgumentNullException`**
→ The `EmittedPackMod` ctor signature changed and `CustomAssetPack`'s
`GetConstructor` lookup is no longer finding it. Compare the IL in
`emitAndRegisterPackMarker` against the current `EmittedPackMod` constructor
parameters — both must agree on the parameter types and the IL must `Ldarg_N`
each one in order before the base ctor call.

**Save load throws `CorruptedSaveException` with a trail through
`AllImplementationsOf<IMod>` → `Failed to resolve 'ModManifest'`**
→ Someone registered the emitted Type instead of the prebuilt instance (i.e.
`RegisterDependency(type)` instead of `RegisterInstance(instance)`). DI tries
to auto-construct, can't find `ModManifest` as a service, the resolution
fails, the failure cascades through TerrainManager/TerrainPhysics/TrainTracks.

**Pack loads but recipes don't appear in-game**
→ Verify `RegisterPrototypes` actually ran (check log). If yes, the issue is
on the Python authoring side, not the C# entry — see [MODDING.md](MODDING.md).

**Pack folder has stale `CustomAssets.dll` or `<PackId>.dll` from a previous deploy**
→ The deploy target deletes these on every run, but only if the pack is
listed under `<NewPatternPack>` in `CustomAssetPack.csproj`. Make sure step
(2) of [Wiring the pack into the build](#wiring-the-pack-into-the-build) is
done and re-run the deploy.

**Log shows `Could not load file or assembly 'CustomAssets, Version=...'` when
a pack loads**
→ The pack's `mod_dependencies` is missing `"CustomAssets>=..."`, so Mafi
loaded the pack before the base mod. CLR can't resolve `CustomAssetPackBase`
from the not-yet-loaded `CustomAssets.dll`. Add the dependency to the
manifest.

## When NOT to use CustomAssetPack

Stay on the legacy per-pack-DLL pattern if **any** of the following apply:

- Your pack contains **custom C# code** (a new IConfig, a custom registrar, a
  Harmony patch). The new pattern is C#-codeless; if you need C#, you need a
  per-pack DLL to contain it.
- Your pack's manifest cannot use `non_locking_dll_load: true` for any reason
  (e.g. you need automatic transitive dependency resolution from
  `Assembly.LoadFrom`).
- You ship the pack as a binary blob to users who already have the legacy
  CustomAssets installation. The new pattern requires shipping the full
  shared `CustomAssets.dll` inside every pack folder; for installed users this
  is harmless duplication, but if you're size-sensitive (downloadable archive
  size matters), the legacy ~few-KB-per-pack approach is leaner.

For everything else — pure-Python-content packs that just add recipes,
products, materials, and machines — the `CustomAssetPack` pattern is the
recommended path.
