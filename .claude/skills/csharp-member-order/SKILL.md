# C# Member Order

Reorganise the members of every type declared in a C# file to follow this exact order:

1. **Fields, constants, events, and properties** — before the constructor block.
2. **Static constructor, then instance constructor(s), then finalizer** — the middle anchor.
3. **Methods, operators, conversion operators, indexers** — after the constructor block.
4. **Nested type declarations** (`class`, `struct`, `enum`, `interface`, `record`, `delegate`) — at the very end of the type.

The reorder is layout-only. Never modify access modifiers, signatures, types, attributes, or method bodies.

## How to apply

1. **Pick the target.** If `$ARGUMENTS` contains a file path, use it. Otherwise use the file referenced in the user's IDE selection. If neither is available, ask which file to reorder.
2. **Read the whole file** with the `Read` tool.
3. **For each top-level type** in the file (skip a type entirely if the project memory marks it protected — and report which ones you skipped):
   - Parse the member list.
   - Partition members into the four groups listed above.
   - **Within each group, preserve the original relative order.** Do not sort alphabetically or by access modifier.
   - Move each member together with everything attached above it: XML-doc `///` comments, single-line `//` comments on the immediately preceding line(s), `[Attribute]` blocks, blank lines that visually belong to the member, and any `#region` / `#endregion` markers wrapping it.
4. **Apply changes** with a single `Edit` call per type if possible, replacing the body of the type with the regrouped members.
5. **Verify the build** with the project's existing build command (e.g. `dotnet build ... -clp:ErrorsOnly`). If the build breaks, undo and explain what went wrong instead of guessing further edits.

## Member classification (when in doubt)

| Member kind | Group |
|---|---|
| `const`, `readonly`, `static readonly`, `static` field, instance field | Fields & properties |
| `event`, event with custom add/remove | Fields & properties |
| Auto-property, full property | Fields & properties |
| Static constructor `static Foo()` | Constructor block (always first inside the block) |
| Instance constructor `Foo(...)` | Constructor block |
| Finalizer `~Foo()` | Constructor block (always last inside the block) |
| Method (instance, static, abstract, override, partial) | Methods |
| Operator overload, implicit/explicit conversion | Methods |
| Indexer `this[...]` | Methods |
| Local function | Stays inside its enclosing method (untouched) |
| Nested `class` / `struct` / `enum` / `interface` / `record` | Nested type declarations |
| Nested `delegate` declaration | Nested type declarations |

## Edge cases

- **Partial type**: only reorder the members declared in the file being processed. Do not touch sibling partials.
- **Nested type**: apply the same rule recursively inside each nested type.
- **Single-member file**: skip; nothing to reorder.
- **Generated code** (`<auto-generated>` header): skip and report.
- **`partial class` with `[GenerateSerializer]` / `[ManuallyWrittenSerialization]`**: still reorder, but keep the attribute on the type declaration line — never move attributes off the type.
- **Comment between two members**: the comment moves with whichever member sits **below** it (treat it as a leading comment of that member).
- **Blank lines**: collapse multiple blank lines down to one between members within a group; keep one blank line between groups.

## What NOT to do

- Don't rename anything.
- Don't change access modifiers or visibility.
- Don't sort alphabetically inside a group.
- Don't reformat code (indentation, brace style, line length) — the rule is order-only.
- Don't merge or split partial classes.
- Don't touch files the project memory flags as protected; report them instead.
